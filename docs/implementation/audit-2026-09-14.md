## 0. Главный вопрос: почему на Cloudflare так долго и так странно

**Платформа тут ни при чём.** Долго и странно получается по четырём причинам, которые складываются:

1. **Код наращивается быстрее, чем его можно осмыслить.** За 6 дней в продуктовый код добавлено
   ~85 тыс. строк (удалено ~12 тыс.), в тесты и скрипты — ещё ~40 тыс. Около 14 тыс. строк продукта
   в сутки. Проект вырос больше чем вдвое за неделю. Новая функция не расширяет существующее, а
   отращивает рядом собственный стек из store, codec, контракта, протокола и квитанций.
2. **Заново реализуется то, что Cloudflare уже даёт.** Каноническое решение DEC-003 требует
   использовать управляемые продукты, а в коде ~5 тыс. строк контура Dynamic Routes и ~5,6 тыс. строк
   вокруг вызова модели — цены, расходы, квалификация, — хотя AI Gateway даёт Spend Limits, Dynamic
   Routes и fallback сам.
3. **Бизнес-логика загнана в SQLite.** 310 триггеров и 982 CHECK-ограничения, триггеры разбирают JSON
   в SQL. Лимиты D1 — глубина выражения 100, `SQLITE_NOMEM` — не причина, а симптом.
4. **Модель прав сама себя разрушает.** Права привязаны к моменту выдачи токена Access и к хэшу
   коммита. Они гаснут при каждом входе и каждой выкладке, а выкладки идут каждые 30–60 минут. Агент
   тратит следующие коммиты на «продление».

Ни одно из этого не останавливается гейтами: CI на `main` красный больше полутора суток, гейт
бюджета красный, гейт `launch:code` не видит часть незавершённого.

## 3. Почему слетает аутентификация

Причин три, и они складываются.

### 3.1. Поколение учётных данных = момент выдачи токена (главная)

`packages/cloudflare-access/src/access.ts:399`:

```ts
credential_generation: `cf-access-jwt:${parsed.kid}:${parsed.payload.iat}`
```

Любой новый JWT Cloudflare Access — новый вход, другой браузер или устройство, ротация ключа подписи —
для системы означает **другого владельца**. От этого значения зависят:

| Где | Сколько |
| --- | --- |
| сравнений в TypeScript | **167** |
| файлов TypeScript | 72 |
| столбцов `credential_generation` в D1 | 24 |
| SQL-условий с ним | 32 |

Всё созданное под прежним токеном — гранты, области чтения, сессии исследований, трассы — становится
«чужим». Например, `apps/eliotr-core/src/source-namespace-read-scope-renewal.ts` отказывает при
несовпадении `access.credential_generation !== context.credential_generation`.

В канонической спецификации понятия «credential generation» **нет**. Там модель явного отзыва:
`REAUTH_REQUIRED` при отзыве OAuth, `QUARANTINE_AND_REVOKE`. Привязка каждого права к моменту выдачи
токена — изобретение реализации. (Риск был отмечен для трасс ещё в PR #138; теперь он системный.)

### 3.2. Поколение выкладки = хэш коммита

`scripts/deploy-cloudflare.mjs:101`: если `ELIOTR_DEPLOYMENT_GENERATION` не задан, он становится
`git-${revision}` — новым на каждый коммит. Проверки сравнивают сохранённое поколение с текущим:
`research-configuration-readiness.ts:164`, `research-configuration-status.ts:235,257,292`.
На `deployment_generation` завязаны 93 файла.

Федеративный сервер тоже берёт `DEPLOYMENT_GENERATION` как свою `credential_generation`
(`apps/eliotr-core/src/composition-root.ts:191`): каждая выкладка меняет его идентичность для внешних
клиентов.

### 3.3. Короткие сроки жизни

- Замороженная область чтения — **15 минут** по умолчанию
  (`packages/cloudflare-navigation/src/scope-service.ts:12`).
- Доказательство квалификации модели — 7 дней, и сгорает при каждой выкладке.
- На продление написаны отдельные модули: `source-namespace-read-scope-renewal.ts` (343 строки),
  `research-qualification-renewal.ts`, `research-owner-qualification-renewal.ts` (601 строка),
  окно продления 5 минут (`RENEWAL_WINDOW_MS`) продублировано в двух файлах.

**Итог:** доступ пропадает при новом входе, при каждой выкладке и по таймеру. В истории это видно как
коммиты «renew expired owner workspace access», «renew model qualification in durable owner research
workflows», «restore model spend read and deployment authority rotation».

### 5.2. Гейт `launch:code` видит не всё

`scripts/check-launch-code.mjs` ищет ровно вызовы `unavailable(` (строка 58) и массив
`disabled_slices` (строка 65). Два изменения выпали из его поля зрения:

- WIKI и FEDERATION перенесены в новый массив `partial_slices` (`c58dbb0`, 2026-09-11) — гейт его не

- Федеративные маршруты возвращают `denied("federation.…")` (`a4b4ac8`, 2026-09-12) — гейт ищет только
  `unavailable`.

Важно не перегнуть: **федерация реализована по-настоящему**. `federationApi` при заданных
`FEDERATION_SERVER_PRINCIPAL_REF` и `FEDERATION_CURSOR_HMAC_KEY` собирает реальный
`createFederationService`; `denied()` — запасная ветка. Но ключи заданы только в `env.test`
(`wrangler.jsonc`), в развёрнутой конфигурации федерация выключена — и гейт этого не показывает.
Поэтому «4 блокера» читать как «гейт видит 4», а не «осталось 4».

## 6. Фронтенд

### 6.1. Для человека — по скриншотам живого развёртывания

Интерфейс сделан как **консоль проверки для агента**, а не как инструмент исследователя: каждая
«live acceptance» добавляла на экран ещё один статус, кнопку обновления или вывод доказательства.

- **Наружу торчат внутренности:** бейдж `E0 · OWNER READ` на каждом экране, `git-6f14c0c`,
  `core-v11-owner-orientation`, `search-v4-ai-search-generation-registry`,
  `Proof expiry 2026-09-21T03:10:07.107Z`, `Qualification: Current`, `Model route: dynamic/eliotr-balanced`,
  термины «admitted sources», «read policy», «Corpus Lens», «source bytes», «sampled coverage».
- **Главного действия нет на первом экране.** На «Research» поля для вопроса не видно: сверху описание,
  пустые счётчики «Not queried / 0 resolved», лента активности и таблица конфигурации моделей.
- **Боковая библиотека повторяется на всех четырёх экранах** и занимает треть ширины; на трёх документах
  уже нужна прокрутка.
- **Сломанные элементы:** кнопка сохранения проекта — пустой голубой прямоугольник без текста; подпись
  «Workspace» трижды над одним выпадающим списком.
- **Дубли и противоречия:** четыре кнопки обновления на «Sources»; на «Wiki» одна фраза («Review
  proposals and read saved page text») повторена трижды; элементы «Published» лежат в разделе
  «proposals» под кнопкой «Open proposal»; слово «workspace» означает три разные вещи.
- **Человека делают оператором агента:** «Start a check, copy the instruction to your agent, then check
  the result here».
- **Пять сообщений об одном и том же** при недоступном сервере: «Waiting for the owner workspace»,
  «The owner workspace is not ready yet», «Workspaces appear after the owner service is ready»,
  «Workspace creation options appear when the owner service is ready», «Workspace connection
  unavailable».

Объём PWA: 12 972 строки в 18 панелях (2026-09-08 было ~2 000 строк и 5 панелей), одна страница
`index.astro`, вся разметка собирается в `main.ts` (544 строки).

### 6.2. Эталон — NotebookLM

Три колонки, каждая отвечает на один вопрос:

| Колонка | Вопрос | Что там |
| --- | --- | --- |
| Sources | что у меня есть | плоский список источников с галочками, «Select all», «Add sources» |
| Chat | о чём спросить | сводка по корпусу, готовые вопросы, **поле ввода всегда внизу** со счётчиком источников |
| Studio | что сделать из этого | отчёт, карта, карточки, таблица — глаголы, а не статусы |

Внутренностей на экране нет вообще.

**Бэкенд ELIOT уже умеет всё это, а в одном — сильнее:**

| NotebookLM | ELIOT |
| --- | --- |
| выбор источников | области `SELECTED_SOURCES` / `PROJECT` / `GLOBAL_LIBRARY` |
| чат с ответом по источникам | `research.query`, `research.run` |
| ссылки на источник | **точный фрагмент с байтовой привязкой и проверкой** — честнее NotebookLM |
| Studio | отчёты, публикация Wiki |

Разрыв почти целиком в подаче. Преимущество ELIOT должно выглядеть как «нажал на ссылку — увидел
точный абзац», а не как бейдж `E0` и срок действия доказательства.

### 6.3. Для агента в headless-режиме

- Headless-интерфейс у проекта уже есть: **66 маршрутов API владельца** (из 75 в
  `packages/interfaces/src/routes.ts`). Агенту следует работать через них; интерфейс — тонкая обёртка
  над тем же API.
- Вместо этого агент проверяет продукт через браузер. Драйвер — **один файл на 7 239 строк**
  (`tests/integration/browser/owner-e2e.mjs`); весь `tests/integration/browser/` — 9 636 строк. Кликов в
  драйвере три, селекторов около дюжины. Остальное — журнал фаз, матрица JWT, ротация JWKS, фазы service
  worker, распределение портов. Спецификация `library.spec.ts` описывает 38 фаз-квитанций, проверяющих
  механику инфраструктуры, а не «пользователь спросил и увидел цитату».
- Лежит в `tests/`, поэтому лимит 600 строк на файл его не видит.
- Хорошее: у элементов стабильные атрибуты `data-nav-target`, `data-workspace-view`, `data-source`,
  `data-excerpt`, `data-library-readiness`.

## 7. Оверинжиниринг, петли, костыли

### 7.1. Петли

| Петля | Механизм |
| --- | --- |
| выкатил → сломал → починил → записал | прод как стенд, каждые 30–60 минут |
| выкладка → права сгорают → «renew» → выкладка | поколение = хэш коммита (§3.2) |
| новый вход → «чужой владелец» → «renew» | поколение = `iat` токена (§3.1) |
| квалификация модели → истекла / сгорела → продление | 7 дней и каждая выкладка, ~5,8 тыс. строк |
| тест агента падает → чинит тест | `owner-e2e.mjs`, 82 правки за 6 дней |

### 7.2. Мутирующие схемы и документы

- Миграции переписывают свои же триггеры: 9 раз `DROP TRIGGER`; файлы `0017_investigation_ledger_fix5.sql`,
  `0019_backup_o2_replay_authority_fix.sql`.
- Триггер слишком сложен → режем на части новой миграцией (`0064_…_guard_depth.sql`).
- Любое изменение формы JSON тянет миграцию триггеров: 65 миграций за две недели.
- Документы-реестры переписываются на каждом цикле (§4.2).

### 7.3. Костыли и обход гейтов

- Код ужат в строки на тысячи символов, форматтера нет (§2.3).
- `partial_slices` и `denied()` — мимо гейта `launch:code` (§5.2).
- Красные гейты бюджета, границ и CI не мешают заливать и выкатывать.

## 9. Что делать — по эффекту

**Остановить разрушение, без этого остальное бессмысленно:**

1. **Привязать права к владельцу, а не к токену.** `credential_generation` должно меняться только при
   явном отзыве или смене политики — не при каждом входе (`access.ts:399`) и не при каждой выкладке
   (`deploy-cloudflare.mjs:101`, `composition-root.ts:191`). Одно решение снимает основную массу
   «слетающих» доступов и заметную часть кода продления. Самый дешёвый и самый заметный пункт.
2. **Не выкатывать при красном CI.** PR-гейта нет, значит CI — единственный сторож.
3. **Заставить гейты работать:** вернуть бюджет в зелёное или честно пересмотреть лимиты; научить
   `launch:code` видеть `denied` и `partial_slices`; включить форматтер — строки на тысячи символов
   исчезнут сами.
4. **Остановить наращивание.** Правило для агента: новая функция сначала переиспользует существующие
   store, codec и протокол, а не заводит свои.

**Упростить архитектуру — главный выигрыш в скорости:**

5. **Отдать шлюзу его работу.** Spend Limits и Dynamic Routes настраиваются в AI Gateway, как требует
   DEC-003. Уходят кластер цен и расходов и контур маршрутов — около 6 тыс. строк и вся петля
   квалификации моделей.
6. **Вынести валидацию JSON из триггеров D1 в TypeScript.** В SQL оставить ключи, уникальность и простые
   CHECK. Уходят лимит глубины, `SQLITE_NOMEM` и значительная часть миграций.
7. **Заморозить Rust** до реального M5 — сейчас 16,5 тыс. строк только съедают время CI.

**Интерфейс:**

8. **Headless-контракт для агента** поверх 66 маршрутов API — короткий CLI или MCP «добавь источник →
   спроси → получи цитаты» — вместо браузерного драйвера на 7 тыс. строк; браузеру оставить несколько
   коротких смоук-тестов.
9. **Интерфейс по образцу NotebookLM:** источники с галочками — чат с одним полем ввода и кликабельными
   точными цитатами — результаты. Всю диагностику (схемы, поколения, доказательства, проверку клиента)
   убрать на одну служебную страницу.
