## Cloudflare operator access

The installed Cloudflare plugin was enabled at version 0.1.2. The existing project-local
`cloudflare-api` connection uses the official `https://mcp.cloudflare.com/mcp` endpoint.
`codex mcp login cloudflare-api` completed, and a fresh CLI readback reported OAuth authentication.
Managed MCP requests then returned successful account, Access organization, application inventory
and identity-provider readbacks. The application inventory was empty with coherent pagination.

No API token was created, copied or exported. Account-specific identifiers and OAuth material are
excluded from this public report. Operator records remain local; no duplicate global MCP server was
added. Unrelated Cloudflare projects were not changed.

Billing usage and subscription requests through MCP returned Cloudflare error `10000`. Earlier
Wrangler requests returned HTTP 403. Those observations do not establish the exact provider-side
cause. The current OAuth scope catalog did not contain a billing- or subscription-named scope; no
scope, counter, billing allowance or paid-operation receipt was invented to fill the gap.

The account's existing paid Workers plan was inspected without changing it. The reviewed project
usage envelope is still sealed: inventory success does not prove available spend, and the unknown
billing metrics remain unresolved. No Eliot Worker, Access application, database, bucket or queue
was provisioned by this audit.

The scripted Access transport is an **unmerged checkpoint**. Its account and organization GETs have
passed against the real managed MCP connection. At candidate `6cad5ae`, the empty application
list was still rejected by an overly strict pagination check; that defect remains a review item.
